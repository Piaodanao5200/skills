# 用户程序结构决策（OB / FC / FB / DB）

## R — 原文 (Reading)

> "组织块 (OB) 定义程序的结构。有些 OB 具有预定义的行为和启动事件，但用户也可以创建具有自定义启动事件的 OB。" "功能 (FC) 不具有相关的背景数据块 (DB)……FC 不与任何特定数据块 (DB) 相关联。" "FB 还使用相关联的数据块（称为背景数据块）来保存该 FB 调用实例的数据值。可多次调用 FB，每次调用都采用唯一的背景数据块。调用带有不同背景数据块的同一 FB 不会对其它任何背景数据块的数据值产生影响。"
>
> — Siemens AG，《S7-1200 可编程控制器系统手册》V4.2，ch5.1 p89；ch7.2/7.3 p201–207

## I — 方法论骨架 (Interpretation)

写 S7-1200 程序前，先决定"每段逻辑放进哪种块"，这决定了数据会不会跨扫描丢失、多台设备会不会互相串扰。四类块角色固定：OB 是由事件触发、由操作系统调度的程序入口（启动 OB 跑一次、程序循环 OB 反复跑、中断/错误 OB 事件驱动），OB 之间不能互相调用，也不能被 FC/FB 调用；FC 是无状态的可复用运算块，临时数据放在局部数据栈、块结束即丢失，要长期保存必须写进 M 或全局 DB；FB 自带背景 DB 保存参数与静态数据，值跨扫描保留，同一 FB 配不同背景 DB 就是不同的"实例"，可控制多台同类设备而互不干扰。结构上先选线性还是模块化：多个同类设备用"一个 FB + N 个背景 DB"的模块化可重入模式；只有一次性简单逻辑才用线性。规划调用层级时要记住两条硬边界：从程序循环/启动 OB 出发最多嵌套 16 层，从中断事件 OB 出发最多 6 层。启动期还有两个专属规则：启动 OB 里读过程映像输入 I 恒为 0，要读当前物理电平必须用 `I:P`；启动阶段中断只排队不处理，循环时间监视不执行。

## A1 — 应用示例 (Application Example)

### 示例 1: 三台电机各自独立控制（worked_example，依据 f02/f27 的 walkthrough）
- **类型与来源**: 合成演练——手册提供角色框架与"一 FB 多 DB"模式（ch7.3.4 p207），未给完整项目；以下按手册规则复算，非作者亲历。
- **问题/输入**: 3 台电机，控制逻辑完全相同，但每台需独立保存速度与累计运行时间，互不干扰。
- **方法论的使用**: 选模块化结构；写一个 FB 封装控制逻辑，其 Input/Output/Static（速度、加速时间、运行时间）存入背景 DB；在 OB1 中调用该 FB 三次，每次指定唯一背景 DB（DB1/DB2/DB3）。
- **结论**: 一个 FB + 3 个背景 DB 实现可重入；FB 完成后的数据留在各自背景 DB，互不覆盖。
- **结果**: 演练输出符合手册"调用带不同背景 DB 的同一 FB 不会影响其它背景 DB 数据值"的规则；实际项目运行结果未说明。

### 示例 2: 调用嵌套深度判定（worked_example）
- **类型与来源**: 合成演练，依据 ch5.1 p89 的 16/6 层硬边界。
- **问题/输入**: 从硬件中断 OB 出发，计划调用一层 FC1，再往下调用 FC2……最多能往下几层？
- **方法论的使用**: 从中断事件 OB 出发的嵌套上限为 6 层；从程序循环/启动 OB 出发为 16 层。
- **结论**: 该调用链最多 6 层，超出须在规划阶段拦截。
- **结果**: 与手册边界一致。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?
1. 从零搭建 S7-1200 用户程序，纠结"这段逻辑该放 OB1、FC 还是 FB"。
2. 多台同类设备（电机/泵/阀）要用同一套控制逻辑，不知道怎么复用又不串数据。
3. 程序里数据莫名其妙丢失或"上次的值不见了"，怀疑 FC/FB 用错、背景 DB 没配。
4. 规划调用层级，担心嵌套太深或启动 OB 里读输入读到 0。
5. 决定用线性结构还是模块化结构、要不要建项目库复用块。

### 语言信号 (用户的话里出现这些就应激活)
- "OB/FC/FB/DB 怎么选" / "when to use FB vs FC" / "instance DB"
- "多台设备用同一个功能块" / "reusable function block multiple motors" / "reentrancy"
- "数据丢了 / 值没保存住" / "data not retained / stateless function"
- "能嵌套多少层" / "nesting depth limit" / "startup OB reads zero"
- "线性还是模块化结构" / "linear vs structured programming"

### 与相邻能力的区分（阶段 3 定稿）
- 与 `data-types-addressing` 的区别：那边定"变量是什么类型、地址怎么分配"，本能力定"代码块怎么组织、状态放哪"；数据类型是结构决策的基础（depends-on 的反向：本能力 depends-on 数据类型认知）。
- 与 `realtime-scan-interrupt` 的区别：那边管扫描时序/OB 优先级/中断组态，本能力管块角色与调用结构；中断 OB 是两者交界的事件入口。
- 与 `data-consistency` 的区别：那边解决"多值读写不撕裂"，本能力解决"状态存在哪个块";优化 DB 不匹配导致的丢数据归 data-consistency。
- 与 `system-design-workflow` 的区别：那是七步工程流程，本能力是其中"用户程序结构设计"这一步的细化。

## E — 可执行步骤 (Execution)

**必需输入**: 控制对象数量与是否同类；每段逻辑是否需跨扫描保存状态；是否涉及中断/启动事件；计划的最大调用层级。信息不全时先问"有几台同类设备、要不要记累计值"。
**交付物与完成标准**: 一张结构决策表——每行列出"逻辑段 → 块类型（OB/FC/FB/DB）→ 是否配背景 DB → 数据保存位置"，并附调用层级草图与两条边界核对结论。

1. **列逻辑清单并分类**
   - 完成标准：把需求拆成若干逻辑段，逐段标注"一次性运算 / 需跨扫描保存状态 / 由事件触发"。

2. **定块类型**
   - 完成标准：需跨扫描保存状态且要多实例 → FB + 各自背景 DB；纯运算无状态 → FC；事件入口 → 对应 OB（启动/循环/中断/错误）。
   - 判停条件：若发现 FC 需要"记住上次值" → 改用 FB 或把状态写入全局 DB，不得留在 FC 临时区。

3. **选整体结构**
   - 完成标准：多个同类设备 → 模块化 + 项目库复用；单一简单任务 → 线性。给出"一个 FB + N 背景 DB"或等价方案。

4. **规划调用层级并核对边界**
   - 完成标准：标出每条调用链起点（程序循环/启动 = 16 层上限；中断事件 = 6 层上限），逐链确认不越界。

5. **核对启动期特殊规则**
   - 完成标准：启动 OB 中所有物理输入读取均用 `I:P`（而非 I）；确认启动期中断只排队、循环监视不执行已被纳入设计。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此能力
- 只是查某条指令（如 SQR、PEEK）的语法或参数——那是指令速查，不是结构设计。
- 选 CPU 型号、算功率预算——用 `power-budget-sizing`。
- 解决多变量在中断/HMI 下"值对不上"——用 `data-consistency`。

### 作者在书中警告的失败模式
- **ce10**：把 PLC 当作唯一安全屏障——结构再好也不能替代独立急停/机电超控。
- **ce30**：用户程序或通信改写系统/时钟存储器位——FirstScan、DiagStatusUpdate 等专用位本质是普通 M 区，被写坏后依赖它们的逻辑不会察觉异常。
- **f05/p13**：启动 OB 里读 I 得到 0 却未用 `I:P`，导致启动逻辑误判。

### 作者的盲点 / 时代局限
- 手册锁定 V4.2（2016）；V4.0 起 OB"可中断/不可中断"成为组态项且默认不可中断，迁移旧项目时须复核（见 ce29）。
- 厂商视角：只讲西门子块模型，不涉及与三菱/AB 的程序组织对比。
- 假设读者已具备梯形图/SCL 与电气基础；功能安全（Failsafe）块体系着墨极少。

### 容易混淆的邻近能力
- `data-types-addressing`（变量/地址）、`realtime-scan-interrupt`（时序/中断组态）、`data-consistency`（多值一致性）、`system-design-workflow`（七步工程流程）。
