# 设备更换与版本兼容检查

## R — 原文 (Reading)

> "要将 V3.0 CPU 更新到 V4.2 CPU，必须替换该 CPU 硬件。不能通过固件更新将 V3.0 CPU 更新到 V4.2 CPU……在 STEP 7 中无法将设备从 V4.2 替换为 V3.0……但下载组态后，无法用 V3.0 替换 V4.2。若尚未下载替换后的设备组态，可以撤消替换；下载之后，便无法撤消。"
>
> — Siemens AG，《S7-1200 可编程控制器系统手册》V4.2，附录 D.1「用 V4.2 CPU 更换 V3.0 CPU」p1799–1806

## I — 方法论骨架 (Interpretation)

设备更换的核心风险是"方向不可逆 + 十几处兼容项散落附录"，所以把它固化成有序检查清单。第一原则是方向：只支持 V3.0 硬件 → V4.2 硬件，不能靠固件升级跨越大版本；下载组态后 V4.2 无法换回 V3.0；更换前先归档 V3.0 项目；下载前可撤消、下载后不可撤消（V4.0/V4.1 项目可直接在 V4.2 运行，无需修改）。第二步升级项目：STEP7 V11/V12 必须先升 V13 SP1 再升 V14，不能直接跳；严禁从旧版复制粘贴程序逻辑到 V14——必须整项目升级后再编辑，否则执行意外或编译失败。第三步核对兼容项：密码保护级别映射（写保护→读访问、写/读保护→HMI 访问、V4.2 的"无访问"V3 不存在）；OB 中断属性（V3 默认不可中断，V4.2 可组态）；传送卡不兼容须重建 V4.2 卡；GET/PUT 默认启用；Web 页面须存到指定子文件夹、旧 admin 用户不支持、数据日志"下载并清除"改为下载/重命名/删除。第四步运动控制：V1/V2 库由编译替换为 V3 指令；TO 版本不自动从 V3.0 升 V5.0，须手动选，且轴参数字段大量重命名、块接口/监控表/跟踪都会更新；核对 CPU 版本↔运动控制版本兼容表；指令 RDREC/WRREC/CONV 变化。第五步 HMI：重新编译项目、下载 CPU 与 HMI、按需更新固件。第六步 DB 预留区：V4.0+ 每 DB 增 100 字节预留；下载前在"选项>设置>PLC编程>常规"设为 0 字节，已换设备则逐 DB 属性删除。第七步解除专有技术/序列号复制保护 → 重新编译全部块 → 纠正所有错误 → 下载；OEM 保护块须索取 V4.2 版本。

## A1 — 应用示例 (Application Example)

### 示例 1: V3.0 项目换 V4.2（worked_example，依据 f73 的 walkthrough）
- **类型与来源**: 合成演练——手册附录 D.1 p1799–1806 给出完整流程，未给具体项目；以下按 7 步复算，非作者亲历。
- **问题/输入**: 某 V3.0 项目（STEP7 V12），含 HMI + 运动控制 V3.0 TO + 专有技术保护块，需换 V4.2。
- **方法论的使用**: ①确认方向不可逆、归档项目；②V12→V13 SP1→V14 整项目升级（不复制粘贴）；③核对密码映射与 OB 属性、重建传送卡、GET/PUT；④TO 手动升 V5.0 并处理字段重命名、指令变化；⑤HMI 重编译下载；⑥下载前把 DB 预留区设为 0；⑦解除专有技术保护后重编译全部块、纠正错误、下载（下载前可撤消）。
- **结论**: 覆盖全部兼容点，得出正确顺序与不可逆边界。
- **结果**: 手册给出各兼容表与步骤；实际项目运行结果未说明。

### 示例 2: 撤消 vs 不可回退（worked_example，依据附录 D.1）
- **类型与来源**: 原书规则，p1799。
- **问题/输入**: 换了 V4.2 设备但还没下载组态，能否换回 V3.0？
- **方法论的使用**: 未下载 → 可撤消替换；一旦下载组态 → 无法用 V3.0 替换 V4.2。
- **结论**: 下载动作是不可逆分界线。
- **结果**: 与手册"下载后可撤消性丧失"一致。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?
1. 现场 V3.0 CPU 故障/升级，要用 V4.2 CPU 替换，问能不能换、怎么换。
2. 想通过固件更新把 V3.0 升到 V4.2（错误方向，需纠正）。
3. 换型后项目编译失败/下载失败，怀疑 STEP7 版本或程序逻辑复制粘贴问题。
4. 项目含 HMI/运动控制/专有技术保护块，担心换型后不兼容。
5. 换型后运动控制轴报错、TO 版本不对、DB 值初始化异常。
6. 想知道换型后能否回退到旧 CPU。

### 语言信号 (用户的话里出现这些就应激活)
- "V3.0 换 V4.2 / 换 CPU" / "replace V3.0 CPU / upgrade CPU hardware"
- "固件升级 / 跨版本" / "firmware upgrade / cross version"
- "更换后编译失败 / 下载失败" / "compile failed after replacement / download failed"
- "TO 版本 / 运动控制库" / "technology object version / motion control library"
- "传送卡不兼容 / 密码映射" / "transfer card incompatible / password mapping"
- "能换回去吗 / 回退" / "can I revert / rollback"

### 与相邻能力的区分（阶段 3 定稿）
- 与 `storage-firmware-maintenance` 的区别：那边是卡/固件/复位/备份的日常维护，本能力是"换 CPU 型号"的版本兼容决策流；V3 传送卡不兼容归本能力（composes-with）。
- 与 `power-budget-sizing` 的区别：换 CPU 型号后可能要重算功率预算，是前后衔接（composes-with）。
- 与 `technology-motion-config` 的区别：那边是正常运动控制组态，本能力处理换型时的 TO 版本升级/字段重命名。
- 与 `program-download-debug` 的区别：那边是常规下载调试，本能力的下载是"换型后不可回退"的关键节点。

## E — 可执行步骤 (Execution)

**必需输入**: 现有项目版本与 STEP7 版本；待换 CPU/模块型号；是否含 HMI/运动控制 TO/专有技术保护块/自定义 Web 页；是否已下载组态。信息不全先问。
**交付物与完成标准**: 更换检查清单——7 步逐项打勾 + 不可逆边界告知 + 编译/下载验证结论。

1. **确认方向与归档** — 完成标准：只做 V3.0→V4.2 硬件更换；明确"下载后不可回退"；归档 V3.0 项目；判停条件：想 V4.2→V3.0 或靠固件跨版本 → 告知不支持，停止。
2. **升级项目** — 完成标准：V11/V12 先升 V13 SP1 再升 V14；整项目升级后编辑，不复制粘贴旧逻辑。
3. **核对通用兼容项** — 完成标准：密码映射、OB 中断属性、传送卡重建、GET/PUT 默认启用、Web 页限制逐项确认。
4. **处理运动控制** — 完成标准：V1/V2 库替换为 V3 指令；TO 手动升 V5.0、字段重命名修正；CPU 版本↔运动版本兼容；RDREC/WRREC/CONV 变化核对。
5. **处理 HMI 与 DB 预留区** — 完成标准：HMI 重编译、下载、按需更新固件；下载前把 DB 预留区设为 0 字节（已换设备则逐 DB 删除）。
6. **解除保护、重编译、下载** — 完成标准：解除专有技术/序列号复制保护；重编译全部块、纠正所有错误；OEM 块索取 V4.2 版本；下载前确认可撤消窗口。
7. **验证** — 完成标准：换后项目可下载运行、无编译错误、HMI/运动/DB 行为正常；确认已越过不可回退点。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此能力
- 仅做固件更新或换存储卡——用 `storage-firmware-maintenance`。
- V4.0/V4.1 项目直接在 V4.2 CPU 运行——无需本流程。
- 查订货号/端子排备件套件表——走 reference-tables.md 检索。

### 作者在书中警告的失败模式
- **ce29**：把 V3"时间错误 OB 可中断任何 OB"套到 V4——OB 默认不可中断致保护失效。
- **ce17**：V3.0 传送卡插入 V4.x CPU → 不兼容报错。
- **ce36**：换型后 TO 与驱动器/传感器组态不一致 → 启动报错。
- 复制粘贴旧程序逻辑到 V14 → 执行意外或编译失败（手册明确警告）；忘记删 DB 100 字节预留区 → 下载问题。

### 作者的盲点 / 时代局限
- 手册锁定 V4.2（2016）这一具体升级场景；更新版本（V4.4+）的升级路径须查新版附录 D。
- 厂商视角：只讲西门子 V3→V4.2 路径，不涉及跨品牌迁移。
- 假设读者有完整 V3.0 项目归档；功能安全/网络安全在这次升级的兼容清单中缺席。

### 容易混淆的邻近能力
- `storage-firmware-maintenance`、`technology-motion-config`、`power-budget-sizing`、`program-download-debug`。

## 相关能力（阶段 3 填充）

- composes-with: `storage-firmware-maintenance`, `power-budget-sizing`
- 对照: `technology-motion-config`（换型时的 TO 版本升级）、`program-download-debug`（换型后不可回退的下载节点）
